## Overview

**Blind App** is an accessible-first application providing a set of features focused on enabling people with low or no vision to interact with digital content. Typical features:

* Voice-driven navigation and commands
* High-contrast, large-type themes
* Screen-reader-first markup and ARIA-safe components
* Haptic / audio cues for mobile
* Offline support for essential data

<Callout type="success">
This app prioritizes accessibility from the ground up, ensuring every feature works without visual affordances.
</Callout>

---

## Goals & Principles

1. **Accessibility by default** — everything should work without visual affordances
2. **Predictable keyboard & voice navigation** — users must be able to complete flows using keyboard or voice alone
3. **Performance and reliability** — slow connections and offline use are common; the app must be resilient
4. **Privacy & minimal permissions** — audio/mic access is optional and explained clearly
5. **Composable UI components** — accessible primitives that teams can reuse

---

## Architecture

* **Frontend:** Next.js (MDX for content), React, Tailwind for utility styles. UI primitives are accessible-first
* **Backend:** Lightweight RESTful API (or GraphQL if required); OAuth for auth
* **Persistence:** IndexedDB + localStorage for offline-first experiences
* **Mobile:** Progressive Web App with service worker, optional native wrappers
* **Telemetry:** Opt-in only; keep data minimal and anonymized

<Callout type="info">
The architecture prioritizes offline-first capabilities and progressive enhancement for better accessibility across all devices.
</Callout>

## Getting Started

### Local Development

```bash
# Clone repository
git clone git@github.com:NalinDalal/blind-app.git
cd blind-app

# Install dependencies
pnpm install

# Run development server
pnpm dev
```

Open `http://localhost:3000`. The app ships with a high-contrast theme and voice tutorial enabled by default in `dev` for testing.

### Environment Variables

Create a `.env.local` with at least:

```bash
NEXT_PUBLIC_API_URL=https://api.example.com
NEXT_PUBLIC_VOICE_KEY=your-voice-api-key  # optional
```

### Project Structure

```
/src
  /components  # accessible UI primitives
  /hooks       # custom React hooks
  /lib         # data layer, speech utils
  /pages       # Next.js pages
  /styles      # global styles
  /tests       # test suites
```

<Callout type="warning">
Ensure you have Node.js 18+ and pnpm installed before starting development.
</Callout>

## Accessibility Checklist

Follow this checklist for every screen and component:

- [ ] Proper semantic HTML (landmark roles, headings in order)
- [ ] Keyboard operable: tab order, focus visibility, skip links
- [ ] ARIA used only where semantics are insufficient
- [ ] Focus management for dialogs and route changes
- [ ] Announcements for dynamic content (live regions)
- [ ] Text alternatives for images and icons
- [ ] Sufficient contrast ratios (WCAG AA / large text AAA where feasible)
- [ ] Reduced motion support
- [ ] Clear permission prompts and privacy notices for mic/camera

<Callout type="error">
**Important:** Helpful tools include axe, Lighthouse (Accessibility), NVDA/VoiceOver testing, and ChromeVox. Use them regularly!
</Callout>

## UI Components & Patterns

### Accessible Primitives (Recommended API)

* `VisuallyHidden` — for helper text only read by screen readers
* `Button` — supports `aria-pressed`, `aria-label`, and keyboard activation
* `Dialog` — traps focus, restores focus on close, has `aria-modal` and `role=dialog`
* `LiveRegion` — polite/urgent announcements
* `Listbox` — ARIA-compliant combobox/listbox keyboard interactions
* `SkipLink` — top of page to jump to main content

### Example: VoiceCommandProvider Usage

```jsx
import { VoiceCommandProvider, useVoice } from "../lib/voice"

function App() {
  return (
    <VoiceCommandProvider>
      <MainApp />
    </VoiceCommandProvider>
  )
}

function Search() {
  const { startListening, stopListening, transcript } = useVoice()
  
  return (
    <div>
      <button onClick={startListening} aria-label="Start voice search">
        Start
      </button>
      <button onClick={stopListening} aria-label="Stop voice search">
        Stop
      </button>
      <div aria-live="polite">{transcript}</div>
    </div>
  )
}
```

<Callout type="info">
**Note:** Always show a visible and an ARIA status when voice is active. Offer manual fallback input for users who cannot or prefer not to use voice commands.
</Callout>

## Data Layer & API

### Authentication

* OAuth2 / JWT short-lived tokens
* Ensure tokens are stored in `httpOnly` cookies where possible for security

### REST Contract (Example)

**GET /v1/items** — list accessible items (paginated)

Response:
```json
{
  "items": [
    {
      "id": "123",
      "title": "...",
      "content": "..."
    }
  ],
  "cursor": "abc"
}
```

**POST /v1/feedback** — user-submitted feedback (voice or text)

Request:
```json
{
  "type": "voice|text",
  "content": "...",
  "metadata": {}
}
```

<Callout type="warning">
**Privacy:** Store minimal metadata and encrypt PII at rest. Follow GDPR and accessibility privacy guidelines.
</Callout>

## Testing & QA

1. **Unit tests** for components (React Testing Library + Jest)
2. **Integration tests** for flows (Playwright) — include keyboard-only scenarios
3. **Accessibility tests:** axe-core in CI + manual screen-reader passes (VoiceOver on macOS, NVDA on Windows)
4. **Voice / audio tests:** mock speech APIs and test UI states when audio permission is denied or dropped

<Callout type="error">
**Critical:** CI should fail on serious accessibility regressions. Accessibility is not optional!
</Callout>

## Appendix: Keyboard Map & ARIA Examples

### Keyboard Conventions

* `Tab` / `Shift+Tab` — move forward/backward between interactive elements
* `Enter` / `Space` — activate button or select
* `Esc` — close overlays
* `Alt+M` — open main voice command (example shortcut)

### ARIA Example: Accessible Modal

```html
<div 
  role="dialog" 
  aria-modal="true" 
  aria-labelledby="dialog-title" 
  tabindex="-1"
>
  <h2 id="dialog-title">Confirm Action</h2>
  <p>Are you sure?</p>
  <button>Cancel</button>
  <button>Confirm</button>
</div>
```

<Callout type="info">
For more ARIA patterns and examples, refer to the [W3C ARIA Authoring Practices Guide](https://www.w3.org/WAI/ARIA/apg/).
</Callout>
